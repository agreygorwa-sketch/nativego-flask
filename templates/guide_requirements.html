NativeGo — All 19 Requirements

Every thing the system must do. Each row shows what you give it, what the system does, and what you see after. The wording is the document's own: Table 4.1, Functional requirements of the NativeGo web platform.

Tourist — FR-01 to FR-08

IDRequirementInput → Process → Output
FR-01Tourist: register an accountName, email, password → validate input, hash password, create account → account created, session started
FR-02Tourist: log in and log outEmail, password → verify hash, open session; clear session on logout → access to tourist pages / session ended
FR-03Tourist: search verified providers by location and serviceLocation, service type, availability filter → query verified providers, rank by proximity → provider list with ratings
FR-04Tourist: view provider profileProvider selection → fetch profile, services, reviews → full profile page
FR-05Tourist: send a service requestService type, description, meeting point, time → create pending request, notify provider → request confirmation with status tracking
FR-06Tourist: exchange messages on a requestMessage text → store linked to the request → message appears in the thread
FR-07Tourist: submit a reviewRating, comment → check service completed, store, update aggregates → review published, provider rating updated
FR-08Tourist: report a misbehaving accountReport reason and details → store for administrator review → confirmation, case queued

Local Provider — FR-09 to FR-14

IDRequirementInput → Process → Output
FR-09Provider: register a provider accountName, email, password, services offered → validate, create account and profile → account created, profile hidden pending verification
FR-10Provider: create and edit service profileBio, languages, services, rates, photos → store profile data → profile saved
FR-11Provider: upload verification documentsIdentity / certificate files → type-check, store, mark pending → documents queued for administrator review
FR-12Provider: set availabilityAvailable days and times → store availability → availability reflected in search results
FR-13Provider: accept or decline requestsAccept / decline decision → update request status, notify tourist → status change confirmed
FR-14Provider: view request and booking historyNone → query the provider's requests → chronological history list

Administrator — FR-15 to FR-19

IDRequirementInput → Process → Output
FR-15Administrator: log inAdministrator credentials → verify role, open session → dashboard access
FR-16Administrator: approve or reject verificationsDecision with reason → update provider status, notify provider → provider visible to tourists, or rejected with reason
FR-17Administrator: manage accountsSuspend / activate action → update account flag → account status changed
FR-18Administrator: handle reported casesReport review and moderation decision → apply warning or suspension → case closed; parties notified
FR-19Administrator: view system statisticsNone → aggregate accounts, requests, reviews → statistics dashboard

Non-functional requirements (Table 4.2)

Functional requirements say what the system does. Non-functional requirements say how well it must do it, across all roles.

IDRequirement and targetWhy it matters to this system
NFR-01Performance: pages load in under 3 seconds on modest mobile connectionsTourists on mobile data abandon slow pages; speed decides adoption (Emam & Abdelaal, 2021)
NFR-02Security: passwords salted and hashed; parameterized queries; server-side role checks on every routeThree roles and user-supplied content make this the sharpest risk (OWASP Foundation, 2021)(Alghawazi et al., 2022)
NFR-03Usability: responsive interface, usable on phones, tablets and desktops with no trainingEase of use drives booking intention (Emam & Abdelaal, 2021)(Li et al., 2022)
NFR-04Privacy: location collected only where a feature needs it; never exposed beyond the parties to a requestLocation data is sensitive and shapes continued use (Rodríguez-Priego et al., 2022)(Choi et al., 2023)
NFR-05Reliability: consistent behaviour under repeated and concurrent use; no data loss on failureA platform that loses requests loses trust
NFR-06Compatibility: runs in any modern browser; no download or installationRemoves the biggest adoption barrier for short-stay tourists (Jagatha et al., 2023)
NFR-07Maintainability: modular code (Flask blueprints per module); normalised schemaOne module change without disturbing the rest (Bednarz & Miłosz, 2025)(Hardini et al., 2025)

Source: Table 4.1, Functional requirements, and Table 4.2, Non-functional requirements, in the project document (Chapters 1–4).
